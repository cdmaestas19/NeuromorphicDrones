FLY BRAIN PILOT - flypilot/ : HOW TO SET UP, RUN AND TEST
=========================================================

What this is
  A simulated Crazyflie drone in CrazySim: MuJoCo physics plus the real Crazyflie firmware, a 3D
  window, the drone's own camera view, and Python flight scripts: ordinary flight control, a
  geometric (range-sensor) avoidance policy, and the fly brain (the fruit fly's escape circuit,
  run as a spiking network) as a second avoidance policy. flypilot\README.md explains how it all
  fits together; flybrain\README.md explains the fly brain.

You run everything from a normal Windows terminal (PowerShell, cmd, or the VS Code terminal). The
.cmd files start everything inside WSL for you, so you never have to open WSL yourself. The
commands below assume your terminal is in the repo folder.


1. WHAT YOUR PC NEEDS
---------------------
  - Windows 11, or Windows 10 version 21H2 or newer (needed for WSLg, which shows Linux windows
    on your desktop).
  - A GPU that WSL can use. You do NOT need a gaming GPU. WSL draws through your normal Windows
    graphics driver (DirectX 12), so most NVIDIA, AMD or Intel GPUs from the last several years
    should work, including the integrated graphics in most laptops, as long as the driver is up
    to date.
  - About 3 GB of free disk space inside WSL: the sim and firmware build (~0.8 GB), the flight's
    Python (~0.55 GB), the fly brain's Python, model and connectome data (~1 GB). Training the
    camera network yourself (optional, run.txt test 10) adds ~1 GB.
  - 2 CPU cores are enough for the sim and the geometric policy. The fly brain runs in a process
    of its own and needs most of one more core (~5 ms per 50 ms tick on a free core; with a game
    running it can take 30-40 ms, and its reactions get later), so 4 cores for fly-brain flights.
  - Memory: 8 GB is plenty for flying. Only the brain checks that simulate the whole fly brain
    (brain_reproduce.cmd, brain_validate.cmd) need more: 3-4.3 GB per simulation, run as many
    at once as memory allows.

  What we measured on one PC (RTX 4080, 20 cores), emulating weaker machines:
    GPU, 20 cores ........... sim at real time, camera 20 fps, waypoint flight OK
    GPU, only 4 cores ....... same: real time, 20 fps, flight OK
    GPU, only 2 cores ....... flight OK, timing clean
    GPU, only 1 core ........ flight completed, but the sim fell behind real time at moments
                              (no safety margin)
    NO GPU (CPU drawing) .... sim falls ~10% behind real time and the flight FAILS (drifts or
                              tumbles). A working GPU is the one hard requirement.
  Not tested yet: integrated laptop graphics, AMD, Intel. If you try one, tell the team how it
  went (RTF number and whether the waypoint flight passed).

  launch.cmd prints the graphics renderer it is using, and warns you when there is no GPU.


2. ONE-TIME SETUP
-----------------
  a) Install WSL with Ubuntu (skip if you already have it). In PowerShell run as Administrator:
         wsl --install -d Ubuntu-24.04
     Reboot if asked. Then open "Ubuntu" from the Start menu once, create a Linux username and
     password when it asks, and close it.
     (Ubuntu 22.04 should also work, but 24.04 is what we tested.)

  b) Make sure WSL is current, so Linux windows can open:
         wsl --update

  c) Clone this repo anywhere on Windows, open a terminal in the repo folder, and run:
         flypilot\setup.cmd
     The first run takes about 10-15 minutes. It:
       - installs build tools, graphics libraries and xdotool (which puts the windows on your
         second screen) inside WSL (runs as root, so no password prompt)
       - downloads CrazySim into ~/CrazySim inside WSL, pinned to the version we tested
       - applies our two fixes from flypilot\patches\ (see section 6)
       - creates the Python environment ~/.venvs/flybrain and installs
         flypilot\requirements.txt
       - builds the simulated Crazyflie firmware
       - for the fly brain (flybrain\setup_brain.sh): downloads the fly-brain model with its
         connectome data (~200 MB, into ~/Drosophila_brain_model) and the FlyWire cell-type
         labels (~/flywire_annotations), and creates the brain's own Python environment
         ~/.venvs/flybrain-snn (Brian2)
     It ends with "Setup finished". It is safe to re-run at any time, and you should re-run it
     after every git pull: that is how changes to requirements, system packages and our CrazySim
     patches reach your PC (an old version of a patch is replaced automatically).
     The camera's person / vehicle network comes ready-trained (flypilot\models\); nothing to set
     up for it.

  More than one WSL distro? The scripts use your default one. To pick another, set this first,
  in the same terminal:
         PowerShell:  $env:FLYPILOT_DISTRO = "Ubuntu-24.04"
         cmd:         set FLYPILOT_DISTRO=Ubuntu-24.04
  ("wsl -l -v" lists your distro names.)


3. WAYS OF RUNNING
------------------
  Everything shows up in ONE window, "MuJoCo : Drone scene with obstacles":
      - the 3D view. Left-drag rotates, right-drag pans, scroll zooms.
      - top-left inset: what the drone's own camera sees (gray, 324x244, like the real AI-deck)
      - bottom-left: "RTF: 1.00x" (see test 2)
      - right side, during avoid and deliver runs: the avoidance dashboard (see section 4, test 5)
  During avoid and deliver runs a second window, "Delivery stops", shows the map from above: the
  stops, the planned route, people and the cart (magenta), and the buttons to add and remove stops.

  flypilot\launch.cmd
      Starts the sim and waits. Use it to look around.
      To stop: close the MuJoCo window or press Ctrl-C.

  flypilot\launch.cmd waypoints
      Same as above, then flies the baseline route: take off to 0.5 m, fly a 1.0 x 0.8 m square
      through open floor (the drone turns to face each leg first), and land where it started.
      Takes about 25 s. The terminal prints one line per waypoint. After landing, everything
      stays open until you close the MuJoCo window or press Ctrl-C.
        Ctrl-C DURING the flight = safety stop: the drone lands where it is, then everything
        shuts down. A second Ctrl-C while it is landing cuts the motors.

  HOW EVERY FLIGHT FINDS ITS WAY
      Every flight is a list of stops. Each leg follows a path planned on a MAP: the planner
      routes around every obstacle on the map and keeps 0.3 m away from it. Whatever is NOT on the
      map is the avoidance layer's job. When the avoidance dodges something, the drone re-plans
      from where it ended up. Three maps:
        all        every obstacle is mapped (deliver's default; square; waypoints)
        building   walls, pillars, partitions, but not the crates: the avoidance has to handle
                   them (the "blocked" test)
        none       nothing mapped, straight lines: the avoidance alone (limit testing)
      New tests go in flypilot\routes.py as stops plus a map.

  flypilot\launch.cmd avoid
      The avoidance demo: the "blocked" route on the "building" map, so its first leg runs
      straight at crate3, which the planner doesn't know about. Uses the geometric avoidance
      policy. The avoidance dashboard is on the right of the 3D view, and the "Delivery stops"
      window opens next to it. The drone sidesteps the crate, passes it, visits the other two
      stops, and lands back home. About 50 s. Ctrl-C works the same as above.

  flypilot\launch.cmd avoid --route square
      The avoidance demo on the clear square route, everything mapped. Avoidance should never
      trigger: this is the false-alarm test.

  flypilot\launch.cmd deliver
      No stops yet: YOU pick where the drone goes, like a customer ordering a delivery. The
      drone takes off and hovers over a blue "H" (home). In the "Delivery stops" window:
        left-click the map              adds a stop (an orange numbered marker). The drone
                                        flies to the stops in order on planned paths, hovers 1 s
                                        at each (the drop-off), and the marker turns green.
        click a stop, or its X          removes it; a stop not yet done is cancelled, even while
                                        the drone is on its way
        Go home (or click H)            return home and land once the queued stops are done
                                        (press again to undo)
        Cancel open stops / Clear finished    empty the queue / tidy away finished stops
        Path planner knows: all / building / none    switch the map (it re-plans at once)
      A ring follows the mouse over the map: green = a stop is allowed there, red = refused (too
      close to an obstacle or wall, or outside the room). Double-clicking in the 3D view works the
      same way. With nothing queued, the drone just hovers and waits. The markers exist only in
      the 3D view: the drone's camera and range sensors never see them. Ctrl-C lands the drone
      where it is.

  flypilot\launch.cmd deliver --at 2.5,0 --at 2.5,-0.9 --at 0,-0.9 --return --map building
      The same with the stops given up front (x,y in metres; the drone starts at 0,0), for
      repeatable tests. --return = come home and land after the last stop instead of waiting
      for more. --map picks the map (also works with avoid). You can still add stops in the
      window.

  MOVING OBSTACLES: PEOPLE AND A CART
      These run in the "street" scene: a 12 x 12 m courtyard with a walkway across it (light), a
      road down it (dark, dashed yellow line, zebra crossing), trees, benches, a kiosk, three people
      and a golf-cart-sized cart. The window is then titled "MuJoCo : Street scene with people and a
      cart". The people and the cart follow scripted paths back and forth; the first encounter is
      timed to happen in the same place every run. They are never on the planner's map, so dodging
      them is the avoidance's job. At the end the terminal prints the closest approach to each of
      them and any contacts.
        flypilot\launch.cmd avoid --route headon     a person walks along the walkway at the drone
        flypilot\launch.cmd avoid --route hover      a person walks up behind the hovering drone
        flypilot\launch.cmd avoid --route crossing   a person crosses the drone's path from the side
        flypilot\launch.cmd avoid --route cart       the cart drives down the road across its path
        flypilot\launch.cmd avoid --route lane       the cart drives up the road at the drone while it
                                                     is in the middle of the lane
        flypilot\launch.cmd avoid --route wallside   a crate nobody mapped, on the path along the
                                                     south wall: it must go round on the open side
        flypilot\launch.cmd avoid --route dropoff    the drone cruises at 4.5 m (above everyone) and
                                                     comes down to drop off; a person walks into the
                                                     drop-off point
        flypilot\launch.cmd avoid --route poles      cruising at 4.5 m, a 6 m pole nobody mapped
                                                     stands on the path
        flypilot\launch.cmd avoid --route landing    the stop is where the cart is parked: it waits
                                                     above, then comes down beside it
        flypilot\launch.cmd deliver --scene street   your own stops while people and the cart go
                                                     back and forth the whole time. It cruises at 4.5 m
                                                     between stops and comes down to 0.5 m at each
      Add --policy flybrain to any of these to let the fly brain decide (see THE FLY BRAIN below).
      With two screens the windows open on the one that isn't your main screen. --screen main keeps
      them on the main one; --headless opens no windows at all (for runs while you use the PC for a
      game: nothing pops up or takes the focus).

  THE FLY BRAIN
      flypilot\launch.cmd avoid --route hover --policy flybrain   (or any route, or deliver)
      launch.cmd starts the brain server too (log: flypilot\logs\brain.log). The fly brain sees
      through a 360-degree compound eye: a ring of "ommatidia" every 5 degrees all the way round and
      from straight down to 30 degrees up. Its looming detectors drive the escape circuit of the
      fruit fly's connectome. When the giant fibers fire, the drone makes an escape burst like a
      fly's takeoff: up, sideways away from the threat, and forward or back away from it.
      flybrain\README.md explains it.
      flypilot\brain_reproduce.cmd   checks the brain model against its paper (needs ~5 GB of free
                                     memory per simulation; it runs as many at once as fit)
      flypilot\brain_validate.cmd    checks the drone's cut-out circuit against the whole brain

  WHAT EVERY FLIGHT DOES AROUND THE AVOIDANCE (any policy)
      - A dodge slows down rather than fly into something the eye sees.
      - After climbing to dodge, the drone comes back down only while the eye sees room below it.
      - After each avoidance episode, unmapped static things it met (a crate, not a person) go on
        the planner's map, so the next path goes round them: orange dots on the top views.

  flypilot\launch.cmd avoid --record recordings\blocked.jsonl
      Also saves every decision's inputs and outputs (one line per decision) to
      flypilot\recordings\. Recordings are not committed to git.

  flypilot\bench.cmd recordings\blocked.jsonl [--policy geometric]
      No sim needed. Replays a recording through the policy and the supervisor, checks that the
      decisions come out identical to the recording ("MATCH"), and reports what each decision
      costs in microseconds. Use it after changing a policy (same decisions, lower cost?) and to
      try new policies on recorded flights.

  flypilot\launch.cmd --camera-window [waypoints]
      Also opens the separate "AI-deck camera" window. It reads the same stream a real AI-deck
      sends over WiFi and shows its fps, so it checks that path. Can't be combined with avoid or
      deliver: the camera stream serves one client, and the avoidance demo uses it.

  The individual pieces. Each one keeps its terminal busy, so you need one terminal per piece.
  launch.cmd does all of this in one terminal.
      flypilot\run_sim.cmd     only the sim (3D window). Its output goes to the terminal.
      flypilot\camera.cmd      only the separate camera window. The sim must already be running.
                               q or Esc quits; s saves a snapshot to flypilot\snapshots\.
      flypilot\stop_sim.cmd    kills any leftover sim, dashboard or camera processes. Safe to run
                               any time.
      flypilot\setup.cmd       the one-time setup from section 2.

  Logs
      When started through launch.cmd, the sim, dashboard, camera and fly-brain output go to
      flypilot\logs\sim.log, dashboard.log, camera.log and brain.log. The simulated firmware's console is
      ~/CrazySim/crazyflie-firmware/sitl_make/build/0/out.log inside WSL. In File Explorer that is
      \\wsl.localhost\Ubuntu-24.04\home\<your linux user>\CrazySim\... (use your distro name).

  Exit codes of the flight scripts: 0 = flew and landed, 1 = could not connect,
  2 = safety stop happened.


4. TESTS TO RUN ON A NEW PC (in this order)
-------------------------------------------
  [ ] 1. Setup.  flypilot\setup.cmd ends with "Setup finished".

  [ ] 2. Sim + camera.  flypilot\launch.cmd --camera-window
         - The terminal prints "Graphics: D3D12 (<your GPU name>)". If it prints llvmpipe or a
           "no GPU acceleration" warning, stop here and see section 5.
         - 3D window: a gray room with brown pillars and green crates, and a small drone on the
           floor in the middle. Top-left inset: the drone's gray camera view, with a tall crate
           straight ahead.
         - The bottom-left corner of the 3D window reads "RTF: 1.00x" (anything 0.97-1.03 is
           fine). This is the most important number. RTF is how fast the sim runs compared to
           real time. The firmware runs on the real clock, so below about 0.95 its timing breaks
           and flights fail.
         - Separate camera window: the same view; its top-left corner reads "324x244  20.0 fps"
           (anything 18 or above is fine).
         Close the 3D window; everything should shut down by itself.

  [ ] 3. Flight.  flypilot\launch.cmd waypoints
         Expected terminal output (your times will differ a little):
           INFO    connecting to udp://127.0.0.1:19850
           INFO    estimator converged at (0.00, 0.00, 0.02), yaw 0 deg
           INFO    taking off to 0.50 m
           INFO    waypoint 1/4 (1.0, 0.0) reached in 2.9 s; nearest obstacle 0.63 m (front)
           INFO    waypoint 2/4 (1.0, -0.8) reached in 3.7 s; nearest obstacle 1.95 m (left)
           INFO    waypoint 3/4 (0.0, -0.8) reached in 4.1 s; nearest obstacle 1.75 m (right)
           INFO    waypoint 4/4 (0.0, 0.0) reached in 3.6 s; nearest obstacle 1.04 m (front)
           INFO    landing at (0.00, 0.00)
           INFO    landed
           fly_waypoints.py finished with exit code 0.
         In the 3D window the drone should fly level and smoothly. Any "SAFETY STOP" line means
         the test failed. Note what it says and see section 5.

  [ ] 4. Safety stop.  Run flypilot\launch.cmd waypoints again, and press Ctrl-C once while the
         drone is flying. Expected: "SAFETY STOP: Ctrl-C. Landing now", the drone descends
         straight down, then "landed", "Shutting down...", "Done." cmd may then ask
         "Terminate batch job (Y/N)?"; answer Y.

  [ ] 5. Avoidance.  flypilot\launch.cmd avoid
         Expected terminal output (your numbers will differ a little):
           INFO    orders: stop 1 added at (2.5, 0.0)
           INFO    orders: stop 2 added at (2.5, -0.9)
           INFO    orders: stop 3 added at (0.0, -0.9)
           INFO    avoidance test: route "blocked" on the "building" map, policy "Geometric TTC" ...
           ...
           INFO    taking off to 0.50 m
           INFO    AVOID   episode 1: signal 0.51 >= 0.50 (front ray 0.78 m, TTC 1.9 s)
           INFO    NOMINAL resumed after 7.8 s in AVOID
           INFO    stop 1 (2.5, 0.0) reached in 12.3 s
           INFO    orders: stop 1 delivered
           INFO    stop 2 (2.5, -0.9) reached in 4.7 s
           INFO    orders: stop 2 delivered
           INFO    stop 3 (0.0, -0.9) reached in 7.8 s
           INFO    orders: stop 3 delivered
           INFO    back home
           INFO    landing at (0.00, 0.04)
           INFO    landed
           INFO    3 delivered, 0 skipped with 1 avoidance episode(s)
           avoid_demo.py finished with exit code 0.
         Pass = exactly ONE "AVOID episode" line, no SAFETY STOP, exit code 0. More than one
         episode at the crate means the mode is chattering.
         The "Delivery stops" window shows the same flight from above: the three stops, crate3
         drawn as an orange outline marked "not on map", and the drone's trail turning red where
         it dodges.
         The dashboard on the right of the 3D view, top to bottom:
           - what is making the decision: which sensors the policy reads (green = used), the
             policy, the supervisor (state machine), and the firmware controller. The "360
             compound eye" and "Fly brain" boxes light up only with --policy flybrain (test 9).
           - the supervisor's mode: NOMINAL (green, following the route) or AVOID (red), and in
             AVOID the checklist that must hold before it returns to the route.
           - the avoid signal over the last 15 s, with the enter (0.50) and exit (0.25) lines;
             red bands are time spent in AVOID.
           - a top view: stops, planned route, trail (green = route, red = avoiding), and the
             range-sensor rays.
           - the five range-sensor distances.

  [ ] 6. No false alarms.  flypilot\launch.cmd avoid --route square
         Pass = "3 delivered, 0 skipped with 0 avoidance episode(s)" and exit code 0.

  [ ] 7. Stops you pick.  flypilot\launch.cmd deliver
         The drone takes off and hovers over a blue "H". In the "Delivery stops" window:
           a. Left-click an open spot of the map. An orange "1" appears there (also in the 3D
              view) and the drone flies to it; on arrival it turns green.
           b. Click a spot on the far side of the long partition (the bar north of the H). The
              drone takes a planned path around the partition instead of flying at it: the
              terminal says "stop N: planned ... legs".
           c. Hover over a crate: the ring turns red. Clicking there is refused ("refused ...").
           d. Add a stop, then press its X before the drone gets there: "stop N cancelled", and
              its marker disappears.
           e. Press "building" under "Path planner knows", then add a stop behind a crate. The
              crate now shows "not on map", and the drone has to dodge it (an AVOID episode).
           f. Press "Go home": "will return home when the queue is done". After the last stop
              the drone flies home and lands.
           g. In the 3D view, double-click the floor once: that adds a stop too.
         Expected terminal output (your stops and times will differ):
           INFO    orders: stop 1 added at (1.0, 0.6)
           INFO    stop 1 (1.0, 0.6) reached in 3.8 s
           INFO    orders: stop 1 delivered
           INFO    orders: stop 2 added at (-0.7, 1.6)
           INFO    stop 2: planned 6 legs, 3.6 m (straight line 2.0 m)
           ...
           INFO    orders: will return home when the queue is done
           INFO    back home
           INFO    landing at (-0.02, -0.01)
           INFO    landed
           INFO    3 delivered, 0 skipped with 1 avoidance episode(s)
           avoid_demo.py finished with exit code 0.
         Pass = every stop you added ends "delivered" (or "cancelled" when you cancelled it), no
         SAFETY STOP, exit code 0.
         Also run the scripted version once:
           flypilot\launch.cmd deliver --at 1.0,0.6 --at -0.7,1.6 --at 1.0,0.6 --return
         Pass = "3 delivered, 0 skipped with 0 avoidance episode(s)": both crossings of the
         partition are planned around it.

  [ ] 8. People and a cart.  flypilot\launch.cmd avoid --route headon   (then hover, crossing, cart, lane, wallside)
         The terminal first prints "Scene: street (street.xml)" and the window shows the courtyard,
         the walkway, the road, three people and a red cart. Each run ends with a line like
           closest approach (drone edge to mover edge): person1 0.13 m; contacts: none
         Expected results are in flypilot\README.md (Moving obstacles). Pass = the flight ends
         with exit code 0 and a "closest approach" line; note any contacts. Then run
         flypilot\launch.cmd deliver --scene street and add a few stops on both sides of the road.

  [ ] 9. The fly brain.  flypilot\launch.cmd avoid --route hover --policy flybrain
         (then headon, crossing, cart, lane, dropoff, wallside, square, blocked with --policy flybrain)
         The terminal prints "fly brain ready in N s: escape subcircuit of 3118 neurons ...". In the
         dashboard the sensor boxes light up green (Multi-ranger "up: room to climb", the camera, the
         "360 compound eye", "Fly brain"), a "Route map" box feeds the policy (yellow when the map
         chose the side), and the lower right panel becomes a radar of what the eye sees all round.
         An escape logs
           AVOID   episode 1: signal 0.67 >= 0.50 (giant fibers L 49 R 67 Hz; eye drive ...)
         The maneuver line says what it escaped from: "not over it (a person)" near people, "up over
         it (a vehicle)" from the cart. The flight ends with "fly brain over N ticks: ... brain
         compute X ms per 50 ms tick; ... side chosen by: eye N, map N, ...".
         Pass = exit code 0, square with 0 avoidance episodes (no false alarms), and in wallside the
         drone goes round the crate on the side away from the wall. Note any contacts.

  [ ] 10. The camera's person / vehicle network (optional: the trained weights are in the repo).
         flypilot\camera_train.cmd
         The first run installs its own Python environment (PyTorch, CPU only, ~200 MB). It labels
         the frames of every recorded flight in flypilot\recordings (fly with --record to add some),
         trains for a few minutes, and prints a confusion matrix over flights it held out, then
         "weights -> ...models/camera_kind.npz (numpy forward pass matches PyTorch to ...)".
         Pass = exit code 0 and an accuracy line. With fewer than ~20 recorded street flights the
         numbers mean little.


5. TROUBLESHOOTING
------------------
  No GPU: "no GPU acceleration" warning, RTF well below 1.00x, or flights drift/tumble
     - Update your GPU driver from the NVIDIA / AMD / Intel website. WSL uses it through
       DirectX 12.
     - Then in PowerShell run "wsl --update" and "wsl --shutdown", and try again.
     - Remote Desktop sessions and virtual machines usually have no GPU for WSL. Run on the PC
       itself.

  No windows appear at all
     WSLg is missing or outdated. Run "wsl --update" (Windows 10 needs 21H2 or newer).

  "The sim closed during the flight", and flypilot\logs\sim.log says "X11: Failed to open
  display :0" or "could not initialize GLFW"
     WSL's graphics service (WSLg) didn't start this time. In PowerShell run "wsl --shutdown",
     then launch again.

  "the fly brain is not answering on udp://127.0.0.1:5320"
     Check flypilot\logs\brain.log. "no brain environment": re-run flypilot\setup.cmd.

  The fly brain never reacts to the people or the cart
     Re-run flypilot\setup.cmd after a git pull: the compound eye is part of our CrazySim patch.
     flypilot\logs\sim.log should list "compound eye: 1800 ommatidia".

  The fly brain reacts late; its summary says "answers later than one tick: (many) tick(s)"
     The brain needs about 12 ms of one CPU core per 50 ms tick. Games and other heavy programs
     running at the same time slow it down to 40-45 ms; close them for fly-brain runs.

  "not flying: no simulator answering" or "could not connect"
     The sim isn't running or didn't finish starting. Use launch.cmd, which waits for it. Or run
     flypilot\stop_sim.cmd and start again. Check flypilot\logs\sim.log for errors.

  The camera window stays on "waiting for tcp://127.0.0.1:5050"
     Either the sim is not running, or another client already has the stream: the sim's camera
     bridge serves ONE client at a time, and a second one kicks the first off. Don't run
     camera.cmd during launch.cmd avoid (the avoidance demo is that client).

  No dashboard on the right of the 3D view during launch.cmd avoid
     Check flypilot\logs\dashboard.log. "cannot listen on udp port 5300" means an old dashboard
     is still running: run flypilot\stop_sim.cmd and try again.

  No "Delivery stops" window during avoid or deliver
     It may be behind other windows or on another monitor: check the taskbar. Errors go to
     flypilot\logs\dashboard.log.

  Clicks in the "Delivery stops" window do nothing
     It accepts clicks only once the flight is running (its right side then shows the
     instructions and buttons). A refused stop says why under the buttons and in the terminal.

  The people and the cart stand still in a street test
     Re-run flypilot\setup.cmd after a git pull: moving them is part of our CrazySim patch.
     flypilot\logs\sim.log should list "movers ['cart1', 'person1', 'person2', 'person3']".

  Double-clicking in the 3D view adds nothing
     - Re-run flypilot\setup.cmd after a git pull: the clicking is part of our CrazySim patch.
     - Double-click with the LEFT button, on the floor itself. Double-clicking the drone selects
       the drone instead (that's MuJoCo's own feature).

  "cannot listen for orders on udp port 5310"
     Another avoid/deliver flight is still running. Close it, or run flypilot\stop_sim.cmd.

  Lines like "QFontDatabase: Cannot find font directory" (when running camera.cmd directly)
     Harmless. OpenCV's built-in Qt has no fonts bundled; the viewer doesn't need them.

  setup.cmd fails partway (e.g. a download error)
     Check your internet connection and run it again. It picks up where it left off.

  Something is still running after a crash, or the 3D window is frozen
     flypilot\stop_sim.cmd

  Wrong WSL distro is used
     Set FLYPILOT_DISTRO (section 2).


6. WHAT WE CHANGED IN CRAZYSIM, AND WHY
---------------------------------------
  flypilot\patches\ holds two fixes that setup.cmd applies automatically to the pinned CrazySim
  checkout. Your CrazySim code will therefore differ from upstream in exactly these places:

  crazyflie-firmware\sitl-64bit-tick-stabilizer.patch
     A one-line firmware bug fix. The simulated firmware uses 64-bit timer ticks, but the
     stabilizer kept its wake-up time in a 32-bit variable, so FreeRTOS also read 4 bytes of
     leftover stack memory. Whether that breaks anything depends on how the compiler lays out the
     stack. With ours (GCC 13, Ubuntu 24.04) the stabilizer never sleeps, the firmware freezes at
     "Wait for sensor calibration", and nothing can connect to it.

  crazyflie-simulation\crazysim-wsl-realtime.patch
     Makes the simulator keep real time under WSL, and adds the overlays:
       - the 3D window's text overlay and the drone camera no longer block the physics loop
       - the loop catches up after slow steps
       - the mirror-like floor reflection is turned off. It looks cleaner, saves GPU time, and a
         real drone camera would not see mirrored obstacles.
       - the 3D window shows the drone camera inset, and any side panel another program writes
         to /dev/shm/crazysim_overlay.rgb (that is how the avoidance dashboard gets in).
       - a double-click on the scenery is sent to UDP port 5310, where the flight takes stop
         requests (the Stops window sends to the same port), and markers sent to UDP 5311 are
         drawn into the 3D view only.
       - the scene's people and cart (mocap bodies) move as the flight commands on UDP 5312.
       - each horizontal range sensor casts a level fan of three rays (-10, 0, +10 degrees) and
         reports the nearest hit. A real VL53L1x sees a ~27 degree cone, and CrazySim's single
         thin ray missed box corners until the drone was 0.07 m away.
       - a compound eye: every 5 degrees all the way round, from straight down to 30 degrees up,
         the distance to the first thing in that direction, sent 20 times a second to UDP 5330.
  After a git pull that changes a patch, re-run setup.cmd: it swaps the old patch for the new one.


7. HOW THE AVOIDANCE IS ORGANISED
---------------------------------
  Every control tick (20 Hz):
     sensors + camera frame --> POLICY --> avoid signal (0..1) + dodge velocity
     avoid signal + range clearance --> SUPERVISOR (state machine) --> NOMINAL or AVOID
     NOMINAL: fly the planned path.   AVOID: fly the policy's dodge, then re-plan.
     The firmware keeps it stable.

  avoidance.py   the contract (AvoidancePolicy.step(sensors, frame) -> AvoidCommand) and the
                 supervisor. Enter AVOID at signal >= 0.50; return to the route only after the
                 signal < 0.25 AND clearance > 0.5 m have held for 0.4 s, and never sooner than
                 0.4 s after entering. One threshold would make the drone chatter in and out.
  policies.py    the policies, picked with --policy <name>:
                   geometric  "Geometric TTC": time-to-collision on the range sensors (closing
                              speed = the drone's own motion + how fast each range shrinks, so
                              it also sees things coming at it)
                   flybrain   "Fly brain (connectome)": the compound eye's looming drives the
                              fly's looming detectors in the connectome's escape circuit
                              (flybrain\brain_server.py, its own process); the giant fibers say
                              when to escape, the steering neurons which side to escape from
                 New policies (the other comparison arms) go here, behind the same interface.
  eye.py         the compound eye and its looming, for the fly brain
  avoid_demo.py  flies the stops on planned paths with whichever policy is chosen; never looks
                 inside a policy. It adds the same safety rules around every policy: slow down
                 near mapped obstacles, back out of a dodge that ended too close to something,
                 and keep the setpoint inside the geofence.
  dashboard.py   the panel in the 3D window. It shows whichever policy is running, and which
                 sensors it reads.

  Decision cost. The end goal is a small drone with little computing power, so every decision
  is timed. At the end of each avoid flight the terminal prints "decision cost (sensors + policy
  + supervisor): mean .. us"; bench.cmd gives the same number without the noise of a live flight.
  Measured on the geometric policy: about 3.6 us per decision in replay and about 20-25 us live
  (the live figure includes Python waiting on the radio and camera threads). The control loop allows
  50000 us per decision, so this uses well under 0.1%. Keep new policies plain scalar code with
  no per-tick allocation; that is what ports to C on the drone.


8. NATIVE LINUX (Ubuntu) INSTEAD OF WINDOWS
-------------------------------------------
  From the repo folder:
      sudo bash flypilot/system_deps.sh
      bash flypilot/setup.sh
      bash flypilot/py.sh launch.py               (sim only)
      bash flypilot/py.sh launch.py waypoints     (sim + flight)
